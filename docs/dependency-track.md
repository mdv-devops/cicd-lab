# Настройка Dependency-Track

[← Вернуться к основной документации](../README.md#dependency-track)

Dependency-Track используется для централизованного анализа программных компонентов, управления рисками цепочки поставок программного обеспечения и непрерывного мониторинга уязвимостей.

В рамках проекта Dependency-Track получает SBOM в формате CycloneDX, сформированный с помощью Trivy при сборке контейнерного образа в TeamCity.

В отличие от Trivy, выполняющего сканирование непосредственно во время CI/CD Pipeline, Dependency-Track обеспечивает непрерывный анализ зарегистрированных программных компонентов после завершения сборки.

В данном разделе рассматривается настройка Dependency-Track версии 5.2.2.

Предполагается, что Dependency-Track уже развёрнут и доступен для настройки.

## 1. Первоначальная настройка

Dependency-Track состоит из двух основных компонентов:

| Компонент | Назначение |
|---|---|
| Frontend | Веб-интерфейс для управления проектами, компонентами и результатами анализа |
| API Server | Обработка SBOM, анализ компонентов, синхронизация источников уязвимостей и предоставление REST API |

В рамках лабораторного окружения используются следующие адреса:

| Компонент | Адрес |
|---|---|
| Frontend | `http://<dependency-track-host>:8080` |
| API Server | `http://<dependency-track-host>:8081` |

Откройте веб-интерфейс Dependency-Track и выполните вход с административной учётной записью.

Все дальнейшие настройки выполняются через раздел `Administration`.

Для взаимодействия с TeamCity будет использоваться REST API и отдельная сервисная учётная запись с минимально необходимыми разрешениями.

> **Важно:** для production-окружения рекомендуется использовать HTTPS, ограничивать сетевой доступ к административному интерфейсу и применять отдельные учётные записи для пользователей и автоматизированных систем.

<a name="general-settings"></a>

### 1.1. Общие настройки

Перейдите в раздел `Administration → General`.

Укажите следующие параметры:

| Параметр | Значение |
|---|---|
| Base URL | `http://<dependency-track-host>:8080` |
| Enable unauthenticated SVG badge access | Выключено |
| Enable Default language | Выключено |

**Base URL**

Базовый адрес веб-интерфейса Dependency-Track, используемый для формирования ссылок на проекты и другие ресурсы системы.

В данном параметре указывается адрес Frontend, а не API Server.

**Enable unauthenticated SVG badge access**

Разрешает получение SVG-бейджей проектов без аутентификации.

В рамках проекта данный параметр оставляем выключенным, чтобы не предоставлять неавторизованным пользователям доступ к информации, отображаемой в бейджах.

**Enable Default language**

Позволяет установить язык интерфейса по умолчанию для пользователей, которые не выбрали язык самостоятельно.

Оставляем параметр выключенным. В этом случае при отсутствии пользовательской настройки язык интерфейса определяется настройками браузера.

После заполнения параметров нажмите `Update`.

## 2. Настройка источников уязвимостей

Dependency-Track использует различные источники информации об известных уязвимостях программного обеспечения.

Использование нескольких источников позволяет расширить покрытие анализа и получать дополнительную информацию для оценки рисков.

В рамках проекта рассматриваются следующие источники данных:

| Источник | Назначение |
|---|---|
| NVD | Информация об известных уязвимостях CVE и оценках CVSS |
| EPSS | Оценка вероятности эксплуатации уязвимостей |
| GitHub Advisories | Информация об уязвимостях программных зависимостей |
| OSV | Информация об уязвимостях компонентов open-source экосистем |
| CISA KEV | Каталог известных эксплуатируемых уязвимостей |
| ENISA EU KEV | Европейский каталог известных эксплуатируемых уязвимостей |

Источники данных дополняют друг друга и используются для формирования более полной картины безопасности программных компонентов.

При этом наличие информации об уязвимости в нескольких источниках не обязательно означает наличие нескольких независимых уязвимостей.

<a name="github-advisories"></a>

### 2.1. GitHub Advisories

GitHub Advisories является источником информации об известных уязвимостях программных компонентов, содержащихся в GitHub Advisory Database.

Для получения данных Dependency-Track использует GitHub GraphQL API.

Аутентификация может выполняться двумя способами:

- GitHub Personal Access Token (PAT).
- GitHub App.

В рамках проекта используется GitHub App, позволяющий получать краткоживущие Installation Access Tokens вместо использования постоянного персонального токена.

#### 2.1.1. Подготовка GitHub App

Для подключения необходимо создать GitHub App и получить следующие данные:

- GitHub App ID.
- GitHub App Installation ID.
- GitHub App Private Key.

GitHub App необходимо установить в соответствующей организации или пользовательской учётной записи GitHub.

Для получения публичных данных GitHub Advisory Database предоставление доступа к содержимому репозиториев не требуется.

#### 2.1.2. Подготовка приватного ключа

Dependency-Track требует приватный RSA-ключ в формате PKCS#8.

GitHub предоставляет приватный ключ в формате PKCS#1, поэтому необходимо выполнить его преобразование.

```bash
openssl pkcs8 -topk8 -nocrypt -in github-app.pem -out github-app.pk8.pem
```

Исходный ключ имеет следующий заголовок:

```text
-----BEGIN RSA PRIVATE KEY-----
```

После преобразования:

```text
-----BEGIN PRIVATE KEY-----
```

Полученный приватный ключ необходимо хранить в защищённом месте.

Не допускается добавление приватного ключа в Git-репозиторий или публикация его содержимого в документации.

#### 2.1.3. Создание Secret

Перейдите в раздел:

`Administration → Secrets`

Создайте Secret со следующими параметрами:

| Параметр | Значение |
|---|---|
| Name | `github-advisories-private-key` |
| Value | Содержимое файла `github-app.pk8.pem` |

В дальнейшем данный Secret будет использоваться для аутентификации GitHub App.

#### 2.1.4. Настройка GitHub Advisories

Перейдите в раздел:

`Administration → Vulnerability Sources → GitHub Advisories`

Укажите следующие параметры:

| Параметр | Значение |
|---|---|
| Enabled | Включено |
| Alias Synchronization Enabled | Включено |
| GraphQL API URL | `https://api.github.com/graphql` |
| API Token | Не задан |
| GitHub App ID | `<github-app-id>` |
| GitHub App Installation ID | `<github-app-installation-id>` |
| GitHub App Private Key | `github-advisories-private-key` |

**Enabled**

Включает синхронизацию данных об уязвимостях из GitHub Advisory Database.

**Alias Synchronization Enabled**

Включает синхронизацию альтернативных идентификаторов уязвимостей, например GHSA и CVE.

Это позволяет Dependency-Track устанавливать связи между записями об одной и той же уязвимости, полученными из различных источников.

**GraphQL API URL**

Адрес GitHub GraphQL API, используемый для получения информации об уязвимостях.

**API Token**

Оставляем незаполненным, поскольку для аутентификации используется GitHub App.

Одновременное использование PAT и GitHub App не предусмотрено.

**GitHub App ID**

Уникальный идентификатор созданного GitHub App.

**GitHub App Installation ID**

Идентификатор установки GitHub App, используемый для получения временных Installation Access Tokens.

**GitHub App Private Key**

Secret, содержащий приватный ключ GitHub App в формате PKCS#8.

После заполнения параметров сохраните настройки.

#### 2.1.5. Синхронизация данных

После включения источника Dependency-Track выполняет синхронизацию данных из GitHub Advisory Database.

Полученная информация сохраняется во внутренней базе данных Dependency-Track и используется при анализе зарегистрированных программных компонентов.

Первоначальная синхронизация может занимать значительное время в зависимости от объёма данных и производительности сервера.

Последующие синхронизации обеспечивают актуализацию информации об известных уязвимостях.

### 2.2. NVD (National Vulnerability Database)

National Vulnerability Database (NVD) — база данных известных уязвимостей, поддерживаемая Национальным институтом стандартов и технологий США (NIST).

NVD предоставляет следующую информацию:

- Идентификаторы уязвимостей CVE.
- Описание уязвимостей.
- Оценки критичности CVSS.
- Информацию о затронутых программных компонентах.
- Классификацию слабых мест программного обеспечения (CWE).
- Ссылки на дополнительные источники информации.

Dependency-Track загружает данные NVD во внутреннюю базу данных для последующего анализа зарегистрированных программных компонентов.

#### 2.2.1. Настройка NVD

Перейдите в раздел:

`Administration → Vulnerability Sources → NVD`

Укажите следующие параметры:

| Параметр | Значение |
|---|---|
| Enabled | Включено |
| CVE Feeds URL | `https://nvd.nist.gov/feeds` |

**Enabled**

Включает синхронизацию данных об уязвимостях из NVD.

**CVE Feeds URL**

Адрес источника данных CVE, используемый Dependency-Track для загрузки информации об уязвимостях.

Источник должен предоставлять файлы в формате JSON 2.0.

В рамках проекта используется официальный источник данных NVD.

Для данного способа загрузки данных отдельный API Key не требуется.

После заполнения параметров нажмите `Save`.

#### 2.2.2. Проверка подключения и синхронизация

Для проверки доступности источника нажмите `Test`.

Для запуска первоначальной синхронизации нажмите `Mirror now`.

Первоначальная синхронизация может занимать значительное время, поскольку Dependency-Track загружает и обрабатывает большой объём информации об известных уязвимостях.

После завершения синхронизации рядом с кнопкой `Mirror now` отображается информация о времени последнего обновления данных.

В дальнейшем Dependency-Track автоматически обновляет локальную базу уязвимостей.

Полученные данные используются Internal Analyzer при анализе программных компонентов.

<a name="osv"></a>

### 2.3. OSV (Open Source Vulnerabilities)

Open Source Vulnerabilities (OSV) — открытая база данных уязвимостей программных компонентов с открытым исходным кодом.

OSV предоставляет информацию об известных уязвимостях с привязкой к конкретным пакетам, версиям и программным экосистемам.

Dependency-Track использует OSV в качестве дополнительного источника информации об уязвимостях программных зависимостей.

#### 2.3.1. Настройка OSV

Перейдите в раздел:

`Administration → Vulnerability Sources → OSV`

Укажите следующие параметры:

| Параметр | Значение |
|---|---|
| Enabled | Включено |
| Alias Synchronization Enabled | Выключено |
| Incremental Mirroring Enabled | Включено |
| Data URL | `https://storage.googleapis.com/osv-vulnerabilities` |
| Ecosystems | `NuGet` |

**Enabled**

Включает синхронизацию данных об уязвимостях из OSV.

**Alias Synchronization Enabled**

Управляет синхронизацией альтернативных идентификаторов уязвимостей, позволяющих устанавливать связи между записями из различных источников.

В рамках текущей конфигурации данный параметр оставляем выключенным.

**Incremental Mirroring Enabled**

Включает инкрементальную синхронизацию данных.

При включённом параметре Dependency-Track загружает только новые или обновлённые записи об уязвимостях с момента предыдущей синхронизации.

При выключенном параметре выполняется полная синхронизация при каждом запуске.

Использование инкрементальной синхронизации позволяет:

- Сократить объём загружаемых данных.
- Уменьшить время последующих синхронизаций.
- Снизить нагрузку на сервер Dependency-Track.
- Обеспечить регулярное обновление базы уязвимостей.

**Data URL**

Адрес источника данных OSV.

В рамках проекта используется официальный источник данных, размещённый в Google Cloud Storage.

Для загрузки данных из данного источника отдельный API Key не требуется.

**Ecosystems**

Определяет программные экосистемы, для которых необходимо синхронизировать информацию об уязвимостях.

Нажмите `Add Ecosystem` и добавьте:

`NuGet`

Поскольку приложение разработано на платформе .NET и использует NuGet для управления программными зависимостями, в рамках проекта достаточно синхронизировать данные для данной экосистемы.

При дальнейшем расширении проекта могут быть добавлены другие экосистемы, например:

| Экосистема | Назначение |
|---|---|
| NuGet | .NET |
| npm | JavaScript / TypeScript |
| Maven | Java |
| PyPI | Python |
| Go | Go |
| crates.io | Rust |

Ограничение списка экосистем позволяет избежать загрузки данных, не относящихся к используемым в проекте технологиям.

После заполнения параметров нажмите `Save`.

#### 2.3.2. Синхронизация данных

Для запуска первоначальной синхронизации нажмите `Mirror now`.

Dependency-Track загрузит информацию об известных уязвимостях для выбранной экосистемы `NuGet`.

После завершения синхронизации рядом с кнопкой `Mirror now` отображается информация о времени последнего обновления данных.

В дальнейшем Dependency-Track автоматически выполняет инкрементальную синхронизацию.

Полученные данные используются при анализе программных компонентов, зарегистрированных в Dependency-Track после загрузки SBOM.

### 2.4. Known Exploited Vulnerabilities (KEV)

Known Exploited Vulnerabilities (KEV) — каталоги известных уязвимостей, эксплуатация которых подтверждена на практике.

Использование данных KEV позволяет учитывать не только оценку критичности уязвимости (CVSS), но и наличие подтверждённых фактов её эксплуатации.

В рамках проекта используются следующие источники:

| Источник | Назначение |
|---|---|
| CISA KEV | Каталог известных эксплуатируемых уязвимостей, поддерживаемый агентством CISA |
| ENISA EU KEV | Европейский каталог известных эксплуатируемых уязвимостей, поддерживаемый агентством ENISA |

Данные KEV используются для дополнительной оценки рисков и определения приоритетов устранения обнаруженных уязвимостей.

<a name="cisa-kev"></a>

#### 2.4.1. CISA KEV

CISA Known Exploited Vulnerabilities Catalog — каталог известных эксплуатируемых уязвимостей, поддерживаемый Cybersecurity and Infrastructure Security Agency (CISA).

Перейдите в раздел:

`Administration → KEV Sources → CISA KEV`

Укажите следующие параметры:

| Параметр | Значение |
|---|---|
| Enabled | Включено |
| Feed URL | `https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json` |

**Enabled**

Включает синхронизацию данных из каталога CISA KEV.

**Feed URL**

Адрес официального источника данных CISA KEV в формате JSON.

Для загрузки данных из данного источника отдельный API Key не требуется.

После заполнения параметров нажмите `Save`.

Для запуска первоначальной синхронизации нажмите `Mirror now`.

После завершения синхронизации рядом с кнопкой `Mirror now` отображается информация о времени последнего обновления данных.

В дальнейшем Dependency-Track автоматически актуализирует данные каталога.

Наличие уязвимости в каталоге CISA KEV является дополнительным фактором при оценке риска и определении приоритета её устранения.

В рамках текущей архитектуры наличие уязвимости в каталоге KEV само по себе не является блокирующим условием CI/CD Pipeline.

#### 2.4.2. ENISA EU KEV

ENISA EU Known Exploited Vulnerabilities (EU KEV) — европейский каталог известных эксплуатируемых уязвимостей, поддерживаемый European Union Agency for Cybersecurity (ENISA).

Данный источник дополняет CISA KEV и предоставляет дополнительную информацию для оценки рисков и определения приоритетов устранения уязвимостей.

Перейдите в раздел:

`Administration → KEV Sources → ENISA EU KEV`

Укажите следующие параметры:

| Параметр | Значение |
|---|---|
| Enabled | Включено |
| Feed URL | `https://raw.githubusercontent.com/enisaeu/CNW/main/eukev/eukev.json` |

**Enabled**

Включает синхронизацию данных из каталога ENISA EU KEV.

**Feed URL**

Адрес официального источника данных ENISA EU KEV в формате JSON, размещённого в GitHub-репозитории ENISA.

Для загрузки данных из данного источника отдельный API Key не требуется.

После заполнения параметров нажмите `Save`.

Для запуска первоначальной синхронизации нажмите `Mirror now`.

После завершения синхронизации рядом с кнопкой `Mirror now` отображается информация о времени последнего обновления данных.

В дальнейшем Dependency-Track автоматически актуализирует данные каталога.

Совместное использование CISA KEV и ENISA EU KEV позволяет расширить покрытие информации об известных эксплуатируемых уязвимостях.

Данные обоих каталогов используются для дополнительной оценки рисков и определения приоритетов устранения уязвимостей.

В рамках текущей архитектуры данные KEV используются для мониторинга и не являются самостоятельным блокирующим условием CI/CD Pipeline.

### 3.2. Sonatype OSS Index

Sonatype OSS Index — внешний анализатор уязвимостей программных компонентов с открытым исходным кодом.

Dependency-Track использует Sonatype OSS Index для получения дополнительной информации об известных уязвимостях программных зависимостей.

В отличие от Internal Analyzer, использующего внутреннюю базу данных Dependency-Track, Sonatype OSS Index выполняет анализ посредством обращения к внешнему REST API.

#### 3.2.1. Подготовка API Token

Для аутентификации в Sonatype OSS Index используется Sonatype Personal Access Token (PAT).

Перейдите на официальный сайт:

[Sonatype Guide](https://guide.sonatype.com/)

Создайте учётную запись или выполните вход с помощью существующей учётной записи GitHub или Google.

В правом верхнем углу откройте меню пользователя и перейдите в раздел:

`User Tokens → Generate Token`

Также можно воспользоваться прямой ссылкой:

[Sonatype Guide — User Tokens](https://guide.sonatype.com/settings/tokens)

Укажите следующие параметры:

| Параметр | Значение |
|---|---|
| Token Name | `dependency-track` |
| Expiration | `90 days` |

Нажмите `Generate Token`.

Скопируйте сгенерированный Personal Access Token и сохраните его в защищённом месте.

> **Важно:** значение токена отображается только в момент его создания. После закрытия окна повторно получить значение токена невозможно.

В рамках проекта рекомендуется использовать отдельный токен для интеграции с Dependency-Track.

Использование отдельного токена позволяет:

- Изолировать учётные данные интеграции.
- Контролировать срок действия токена.
- Выполнять ротацию токена.
- Отзывать токен независимо от других интеграций.

При использовании Sonatype Personal Access Token указание Username в настройках Dependency-Track не требуется.

Полученный токен необходимо добавить в хранилище Secrets Dependency-Track, настройка которого описана в следующем подразделе.

**Официальная документация:**

- [Manage Guide User Tokens](https://help.sonatype.com/en/manage-guide-user-tokens.html)
- [Using Guide Personal Access Tokens with OSS Index API Integrations](https://help.sonatype.com/en/using-guide-personal-access-tokens-with-oss-index-api-integrations.html)

#### 3.2.2. Создание Secret

Перейдите в раздел:

`Administration → Secrets`

Создайте Secret со следующими параметрами:

| Параметр | Значение |
|---|---|
| Name | `sonatype-api-key` |
| Value | Sonatype Personal Access Token |

Не допускается публикация токена в исходном коде, конфигурационных файлах Git-репозитория или документации.

Перейдите в раздел:

`Administration → Analyzers → Sonatype OSS Index`

Укажите следующие параметры:

| Параметр | Значение |
|---|---|
| Enabled | Включено |
| Alias Synchronization Enabled | Включено |
| API URL | `https://api.guide.sonatype.com` |
| Username | Оставить пустым |
| API Token | `sonatype-api-key` |

**Enabled**

Включает анализ программных компонентов с использованием Sonatype OSS Index.

**Alias Synchronization Enabled**

Включает синхронизацию альтернативных идентификаторов уязвимостей.

Это позволяет Dependency-Track устанавливать связи между записями об одной и той же уязвимости, полученными из различных источников.

**API URL**

Адрес REST API Sonatype, используемый для получения информации об уязвимостях программных компонентов.

В рамках текущей конфигурации используется:

`https://api.guide.sonatype.com`

**Username**

Имя пользователя для аутентификации в Sonatype OSS Index.

При использовании Sonatype Personal Access Token данный параметр является необязательным.

В рамках проекта оставляем поле пустым.

**API Token**

Secret, содержащий Sonatype Personal Access Token.

В выпадающем списке выберите ранее созданный Secret:

`sonatype-api-key`

После заполнения параметров нажмите `Save`.

<a name="trivy-analyzer"></a>

### 3.3. Trivy Analyzer

Trivy Analyzer позволяет Dependency-Track использовать внешний Trivy Server для обнаружения известных уязвимостей в программных компонентах.

В рамках проекта Trivy используется в двух независимых механизмах анализа:

| Компонент | Назначение |
|---|---|
| Trivy CLI в TeamCity | Сканирование зависимостей и контейнерных образов во время CI/CD Pipeline |
| Trivy Server в Dependency-Track | Анализ зарегистрированных программных компонентов в рамках непрерывного мониторинга |

Использование Trivy Analyzer позволяет дополнить результаты других анализаторов информацией об уязвимостях системных пакетов и программных зависимостей.

#### 3.3.1. Подготовка API Token

Предполагается, что Trivy Server уже развёрнут, доступен по сети и настроен для работы с аутентификацией по токену.

В отличие от Sonatype OSS Index, для получения токена Trivy не требуется регистрация во внешнем сервисе.

Токен генерируется самостоятельно и задаётся в конфигурации Trivy Server.

Для генерации случайного токена можно использовать следующую команду:

```bash
openssl rand -hex 32
```

На стороне Trivy Server токен может быть задан через переменную окружения:

```text
TRIVY_TOKEN=<trivy-api-token>
```

Также токен может быть передан при запуске Trivy Server через параметр `--token`.

Значение токена в конфигурации Trivy Server и в Dependency-Track должно совпадать.

Если Trivy Server уже настроен с использованием токена, необходимо использовать существующее значение.

#### 3.3.2. Создание Secret

Перейдите в раздел:

`Administration → Secrets`

Создайте Secret со следующими параметрами:

| Параметр | Значение |
|---|---|
| Name | `trivy-api-token` |
| Value | Токен, используемый Trivy Server |

Не допускается хранение токена в открытом виде в Git-репозитории или публикация его значения в документации.

#### 3.3.3. Настройка Trivy Analyzer

Перейдите в раздел:

`Administration → Analyzers → Trivy`

Укажите следующие параметры:

| Параметр | Значение |
|---|---|
| Enabled | Включено |
| API URL | `http://trivy:4954` |
| API Token | `trivy-api-token` |
| Ignore Unfixed | Выключено |
| Scan Library | Включено |
| Scan OS | Включено |

**Enabled**

Включает анализ программных компонентов с использованием Trivy Server.

**API URL**

Адрес Trivy Server, используемый Dependency-Track для выполнения анализа.

В рамках лабораторного окружения Dependency-Track API Server и Trivy Server находятся в общей Docker-сети.

Поэтому для взаимодействия используется внутреннее DNS-имя сервиса:

`http://trivy:4954`

Публикация порта Trivy Server за пределами Docker-сети для данной интеграции не требуется.

**API Token**

Secret, содержащий токен аутентификации Trivy Server.

В выпадающем списке выберите ранее созданный Secret:

`trivy-api-token`

**Ignore Unfixed**

Определяет необходимость исключения из результатов анализа уязвимостей, для которых отсутствуют исправления.

В рамках проекта данный параметр оставляем выключенным.

Это позволяет получать информацию обо всех обнаруженных уязвимостях, включая те, для которых исправления ещё не выпущены.

Отсутствие исправления не означает отсутствие риска эксплуатации уязвимости.

**Scan Library**

Включает анализ программных библиотек и зависимостей приложения.

В рамках проекта данный параметр используется в том числе для анализа NuGet-пакетов.

**Scan OS**

Включает анализ пакетов операционной системы.

Данный параметр позволяет обнаруживать уязвимости системных компонентов, входящих в состав контейнерного образа.

После заполнения параметров нажмите `Save`.

#### 3.3.4. Принцип работы

После загрузки SBOM в Dependency-Track выполняется анализ зарегистрированных программных компонентов.

Dependency-Track обращается к Trivy Server для получения информации об известных уязвимостях.

```text
TeamCity
    │
    │ CycloneDX SBOM
    ▼
Dependency-Track API Server
    │
    │ Vulnerability Analysis
    ▼
Trivy Server
    │
    ▼
Trivy Vulnerability Database
```

Trivy Server использует собственную базу данных уязвимостей, которая регулярно обновляется.

Полученные результаты анализа используются Dependency-Track для формирования информации об уязвимостях зарегистрированных компонентов.

При этом Dependency-Track не требуется загружать контейнерный образ из Docker Hub для выполнения данного анализа.

#### 3.3.5. Роль Trivy Analyzer в DevSecOps Pipeline

Trivy Analyzer дополняет существующие проверки безопасности, выполняемые в TeamCity.

| Характеристика | Trivy CLI в TeamCity | Trivy Analyzer в Dependency-Track |
|---|---|---|
| Момент анализа | Во время выполнения Pipeline | После регистрации компонентов |
| Объект анализа | Исходный код, зависимости и контейнерный образ | Компоненты, зарегистрированные в SBOM |
| Блокирование Pipeline | Да, при обнаружении HIGH или CRITICAL уязвимостей согласно Security Gate | Нет |
| Анализ ранее собранных версий | При повторном сканировании | В рамках непрерывного мониторинга |
| Уязвимости без исправлений | Учитываются | Учитываются |

Таким образом, Trivy CLI обеспечивает контроль безопасности на этапе сборки, а Trivy Analyzer в Dependency-Track позволяет отслеживать появление новых уязвимостей после завершения CI/CD Pipeline.

## 4. Настройка доступа для TeamCity

Для автоматической загрузки SBOM из TeamCity необходимо настроить аутентификацию и авторизацию в Dependency-Track.

В рамках лабораторного окружения используется следующий механизм:

- Отдельная Team для логической группировки сервисных учётных записей.
- Отдельная Service Account для интеграции с TeamCity.
- Назначение разрешений непосредственно на уровне Service Account.
- API Key с ограниченным сроком действия.

> **Важно:** данный способ аутентификации выбран в рамках лабораторного окружения. Для production-окружения рекомендуется дополнительно рассмотреть использование Workload Identity Federation, краткоживущих учётных данных и централизованного управления секретами.

В рамках проекта применяется принцип наименьших привилегий (Principle of Least Privilege).

<a name="create-team"></a>

### 4.1. Создание команды

Перейдите в раздел:

`Administration → Access Management → Teams`

Создайте новую Team со следующими параметрами:

| Параметр | Значение |
|---|---|
| Team Name | `teamcity` |
| API Keys | Не создаются |
| Permissions | Не назначаются |
| Mapped LDAP groups | Не настроено |
| Mapped OpenID Connect Groups | Не настроено |

Команда `teamcity` используется для логической группировки сервисных учётных записей, относящихся к интеграции с TeamCity.

На данном этапе разрешения и API Keys не создаются.

API Keys непосредственно на уровне Team не используются, поскольку такие ключи не имеют срока действия и не позволяют однозначно связать использование ключа с конкретным потребителем.

Разрешения и API Key будут настроены непосредственно на уровне Service Account.

### 4.2. Создание сервисной учётной записи

|---|---|

| Email | `teamcity@example.com` |
| Suspended | Выключено |

**Username**

Имя сервисной учётной записи, используемой для интеграции с TeamCity.

**Email**

### 4.3. Настройка разрешений Service Account

| Permission | Назначение |
|---|---|

**BOM_UPLOAD**

Предоставляет разрешение на загрузку SBOM через REST API Dependency-Track.

Данное разрешение необходимо для выполнения Build Step `Upload SBOM to Dependency-Track` в TeamCity.

**PROJECT_CREATION_UPLOAD**

Предоставляет разрешение на автоматическое создание проекта при загрузке SBOM с параметром:

`autoCreate=true`

Поскольку Git commit SHA используется в качестве версии проекта, при загрузке SBOM для новой ревизии приложения необходимо обеспечить возможность автоматического создания соответствующей версии проекта.

Дополнительные административные разрешения сервисной учётной записи не предоставляются.

В рамках текущего сценария достаточно двух указанных разрешений.

<a name="api-key"></a>

### 4.5. Создание API Key

В настройках сервисной учётной записи `svc:teamcity` перейдите в раздел `API Keys`.

Нажмите `+` для создания нового API Key.

Создайте ключ со следующими параметрами:

| Параметр | Значение |
|---|---|
| Название ключа | `teamcity-sbom-upload` |
| Срок действия | 90 дней |

Скопируйте сгенерированный API Key и сохраните его в защищённом месте.

Полученный API Key будет использоваться TeamCity для аутентификации при обращении к REST API Dependency-Track.

В TeamCity ключ хранится в параметре:

`env.DTRACK_API_KEY`

Тип параметра — `Password`.

**Управление жизненным циклом API Key**

Dependency-Track отображает следующую информацию о созданном ключе:

| Параметр | Назначение |
|---|---|
| Public ID | Публичный идентификатор ключа |
| Created | Дата и время создания |
| Last Used | Дата и время последнего использования |
| Expires | Дата и время окончания срока действия |

Public ID не является значением API Key и не может использоваться для аутентификации.

Использование API Key с ограниченным сроком действия позволяет контролировать жизненный цикл учётных данных интеграции.

До истечения срока действия необходимо выполнить ротацию ключа:

1. Создать новый API Key.
2. Обновить защищённый параметр в TeamCity.
3. Проверить успешность загрузки SBOM.
4. Удалить предыдущий API Key.

Не допускается хранение значения API Key в Git-репозитории, исходном коде или документации.

## 5. Интеграция с TeamCity

Интеграция Dependency-Track с TeamCity предназначена для автоматической регистрации программных компонентов приложения после формирования SBOM.

Взаимодействие между системами осуществляется через REST API Dependency-Track с использованием API Key ранее созданной сервисной учётной записи `svc:teamcity`.

### 5.1. Принцип интеграции

Загрузка SBOM выполняется в рамках Pipeline `2: Building & Deployment`.

Последовательность взаимодействия:

```text
TeamCity
    │
    ├── Build
    │
    ├── Trivy Image Scan
    │
    ├── Generate SBOM
    │
    ├── Upload SBOM to Dependency-Track ──► Dependency-Track
    │                                           │
    ├── Push                                    ├── Project Creation
    │                                           ├── SBOM Processing
    └── Cosign Sign & Verify                    ├── Vulnerability Analysis
                                                └── Continuous Monitoring
```

После успешного сканирования контейнерного образа Trivy формирует SBOM в формате CycloneDX JSON.

Сформированный SBOM передаётся в Dependency-Track через REST API:

`POST /api/v1/bom`

Для аутентификации используется HTTP-заголовок `X-Api-Key`.

Dependency-Track автоматически создаёт соответствующую версию проекта, обрабатывает SBOM и выполняет анализ зарегистрированных программных компонентов.

### 5.2. Параметры интеграции

Для взаимодействия с Dependency-Track в TeamCity используются следующие параметры:

| Параметр | Тип | Назначение |
|---|---|---|
| `env.DTRACK_URL` | Text | Адрес API Server Dependency-Track |
| `env.DTRACK_PROJECT_NAME` | Text | Название проекта |
| `env.DTRACK_API_KEY` | Password | API Key сервисной учётной записи |

В рамках лабораторного окружения используется следующая конфигурация:

| Параметр | Значение |
|---|---|
| API Server URL | `http://<dependency-track-host>:8081` |
| Project Name | `cicd-lab` |
| Project Version | Git commit SHA |
| Service Account | `svc:teamcity` |
| SBOM Format | CycloneDX JSON |
| SBOM File | `sbom-report/sbom.json` |

Для взаимодействия с Dependency-Track необходимо использовать адрес API Server, а не Frontend.

API Key должен храниться в TeamCity в защищённом параметре типа `Password`.

### 5.3. Версионирование проектов

В качестве версии проекта в Dependency-Track используется Git commit SHA текущей сборки.

Это позволяет обеспечить связь между следующими компонентами:

- Ревизия исходного кода.
- Сборка TeamCity.
- Контейнерный образ.
- SBOM.
- Версия проекта в Dependency-Track.

Каждая новая ревизия приложения регистрируется в Dependency-Track как отдельная версия проекта.

Таким образом, сохраняется история состава программных компонентов и обеспечивается возможность непрерывного мониторинга ранее собранных версий приложения.

### 5.4. Обработка результатов анализа

Обработка SBOM и анализ программных компонентов выполняются асинхронно на стороне Dependency-Track.

В рамках текущей архитектуры Dependency-Track используется как инструмент непрерывного мониторинга безопасности, а не как блокирующий Security Gate.

| Событие | Влияние на Pipeline |
|---|---|
| Успешная загрузка SBOM | Pipeline продолжает выполнение |
| Ошибка загрузки SBOM | Pipeline завершается с ошибкой |
| Обнаружение уязвимостей в Dependency-Track | Pipeline не блокируется |
| Обнаружение новых уязвимостей после завершения Pipeline | Информация отображается в Dependency-Track |

Блокирующие проверки безопасности контейнерного образа выполняются непосредственно в TeamCity с использованием Trivy.

Dependency-Track дополняет данный механизм непрерывным мониторингом зарегистрированных программных компонентов.
